Methodological principle: the project's current bottleneck is empirical evidence, not architectural sophistication. Reliability/engineering defects found so far have been fixed (see history.md); none of that answers the one question that determines whether this system is worth running: does it provide predictive/ economic value beyond simpler quantitative strategies, after removing leakage, selection bias, and metric artifacts? Intended order of work: clean independent observations → simple baselines → controlled ablations → incremental-value evidence → robustness -- not more complexity first. A higher Sharpe/hit-rate/more sophisticated architecture is not, by itself, sufficient evidence of edge (see the Sharpe-periodicity finding below for a measured example). A component is validated only when its incremental contribution is demonstrated on genuinely separated observations and survives reasonable methodological alternatives.

A. Active research — investment validity

  • Open [CRITICAL][Backtest] No genuine temporal embargo between backfilled training window and live holdout window — Phase 3g's own audit found the gap negative against a 45-day longest resolution horizon; the live-computed embargo_gap_days (Calibration summary) confirms this is still true (re-checked 2026-10-02: -17.3 days, i.e. the windows overlap in wall-clock time) with 100% of live decisions within one horizon's distance of the boundary. Price-momentum/regime persistence (present in both sets) creates a plausible dependency channel.
    What this does/doesn't prove: window overlap and a plausible dependency channel are not the same claim as proven feature-level information leakage -- the project's own point-in-time audit found no actual look-ahead at the feature level. Read this as proof the two samples cannot currently be treated as statistically independent, not proof future information entered a feature. Decision criterion: until a genuinely independent temporal holdout cohort exists, current/past holdout results are directional evidence only, never confirmatory. Fix: introduce a real embargo gap for the next holdout cohort, or keep treating every current/past result as non-confirmatory everywhere a backfilled Sharpe/hit-rate figure is shown. Status (2026-10-02, still Open): option (a) is now real -- a frozen TRAINING_WINDOW_END (2026-09-23) + 45-day embargo defines a clean HOLDOUT_COHORT_START (2026-11-07), surfaced as the Calibration summary's own "Holdout cohort" row below, and run_replay.py now refuses to replay past that boundary without an explicit override. Closes only once that cohort's own holdout_cohort_confirmatory goes true (uncontaminated AND resolved-directional n≥50) -- estimated no earlier than ~2026-11-13, a multi-month wait the user has explicitly accepted.
  • Open [CRITICAL][Backtest] The historical replay's candidate universe is not point-in-time — verified directly in code (2026-10-02): HistoricalReplayService.run() (app/benchmarks/replay.py) still calls get_active_assets() once and reuses TODAY's active-asset list for every simulated historical day, rather than reconstructing which assets would genuinely have been eligible on that historical date. A real hindsight/survivorship effect -- today's asset list reflects which assets turned out to matter.
    Explicitly distinct from an already-fixed, unrelated bug: not the same issue as the Binance historical-fetch date-anchor/pagination bug (fixed -- see history.md's Phase 5f/5m), which made historical OHLCV retrievable but does nothing for which assets were eligible on a given historical day. Do not mark this resolved on the strength of the OHLCV fix. Fix: reconstruct a genuine point-in-time candidate universe if a historical market-cap/ranking source is reachable, or explicitly label every backfilled Sharpe/hit-rate figure as subject to universe-selection bias.
  • Open [HIGH][Quant/Backtest] Simple-baseline / incremental-value ladder — the central open research question — the real question is not "what is the system's Sharpe" but whether each layer of sophistication adds value over the simpler layer beneath it, on the same observations. What already exists (verified 2026-10-02, not building from zero): app/benchmarks/baseline_comparison.py + scripts/run_benchmark_comparison.py already compute BTC buy-and-hold and an equal-weight-universe basket (Sharpe, max drawdown, total return raw/net-of-costs). scripts/run_composite_weights_validation.py already compares the live composite-factor weighting against equal-weight/momentum-only, but only as a correlation/mean-score check, not a full P&L backtest. scripts/run_periodicity_fix.py produced the project's single most important methodology finding to date (below). None of these three share the same assets/dates/cutoff/cost assumptions today -- fragments of a ladder, not a controlled comparison.
    Needed: one controlled comparison (same assets/dates/cutoff/holding-period/cost assumptions/metrics/OOS observations) across progressively more complex approaches: (1) BTC buy-and-hold, (2) equal-weight basket, (3) market-cap-weighted basket, (4) momentum-only, (5) deterministic composite-factor strategy, (6) composite factors + LLM research, (7) full system. Measure incremental predictive accuracy, return, risk-adjusted performance, drawdown, turnover/cost impact, calibration, statistical uncertainty -- and whether each layer adds information conditional on the layer beneath it, not just whether the full stack looks good alone. Known prerequisite: run_periodicity_fix.py is currently scoped to backfilled decisions only (found 2026-09-16, not actioned) -- extend to live decisions too. The headline finding that makes this concrete: old decision-level Sharpe ≈ 1.846 (looked like real edge) -- corrected, periodicity-matched pooled-daily Sharpe ≈ 0.295, nearly identical to BTC buy-and-hold's own daily Sharpe of ≈ 0.313 over the same window. The apparent edge was substantially a metric artifact -- exactly what this ladder exists to catch systematically.
  • Open [HIGH][AI/Quant] LLM incremental-value / ablation test — does the LLM research layer add predictive information beyond deterministic quantitative signals? Compare, using the same observations where feasible: (1) deterministic factors only, (2) + LLM assessments, (3) + adversarial analysis, (4) full Judge pipeline.
    Measure directional accuracy, return, risk-adjusted return, drawdown, turnover, costs, calibration, incremental contribution at each step. Do not conclude the LLM layers add value because their output is sophisticated or because individual narratives read as plausible -- that is exactly the failure mode the LLM-leakage finding below demonstrates models are capable of.
  • Open [HIGH][Quant] Composite factor weights — empirical validation still unresolved — COMPOSITE_FACTOR_WEIGHTS remains a chosen convention, not fit or backtested, and gates which assets every downstream stage even sees.
    Infrastructure vs. validation: the comparison infrastructure is built and real (compute_composite_factor_scores's weights override, run_composite_weights_validation.py) -- that part is done. The empirical validation is not: real joinable sample was n=2 at last check. Subordinate to the baseline-ladder item above (same underlying question, narrower scope) -- do not over-prioritize relative to it.
  • Open [HIGH][Quant] Evidence-value logistic-regression ranking — MIN_SAMPLE_SIZE=50 never cleared; re-checked live 2026-10-02: n=46, unchanged despite 21 more live decisions resolving in the interim, because this script draws only from the fixed 154-row backfilled population (is_backfilled=True).
    Passively waiting will NOT close this gap -- reaching n≥50 needs more backfilled replay, or a deliberate decision to extend this to live decisions (not yet made). n≥50 is an eligibility threshold, not a validation result: once cleared, still need coefficient stability, class balance, uncertainty, OOS performance where possible, multiple-testing concerns, incremental value, and robustness to alternative specifications. Treat every evidence category as unproven until that full check passes, not merely until n≥50.
  • Open [HIGH][AI] LLM self-reported confidence/uncertainty/source agreement — calibration AND incremental information — pure self-reported numbers with no deterministic cross-check (unlike model_agreement), used directly as a Risk Engine sizing input.
    Two distinct, both-unresolved questions: (1) calibration -- does stated confidence predict realized correctness (live-only)? (2) incremental information -- do these numbers predict outcomes after accounting for deterministic signals and other Judge inputs, or are they redundant? Passing (1) alone is not sufficient -- a well-calibrated but redundant signal adds no real value.
  • Open [HIGH][AI] Adversarial (3f) chain — incremental value, not infrastructure — confirmed sequential (bear receives the bull case, scenario receives both), and real replay support now exists (HistoricalReplayService's optional adversarial params, run_replay.py --with-adversarial) -- that part is built.
    Remaining question is purely empirical: does adversarial analysis add incremental predictive value over the Judge's single synthesizing call? That adversarial output is referenced in a thesis is not evidence it improved the decision -- theses can incorporate content without that content changing the directional outcome.
  • Medium Regime robustness / Parameter sensitivity / Cross-asset generalization — kept deliberately concise, not over-specified ahead of evidence: (1) whether any demonstrated edge holds across RISK_ON/RISK_OFF/NEUTRAL or is concentrated in one regime; (2) MAX_CONCURRENT_POSITIONS/MIN_REPLACEMENT_ALPHA_ADVANTAGE sensitivity (same documented-convention-not-backtested status as composite weights); (3) whether any edge generalizes across the universe or concentrates in a handful of assets. All three genuinely depend on the baseline-ladder item existing first to have a real effect size worth slicing.
  • Confirmed [CRITICAL][AI] LLM parametric-knowledge leakage in backfilled decisions -- tested directly, mitigation verified against a real BTC-centered crash, not Done — the Aug 2024 XMR replay demonstrated 2-of-3 assessment models citing an unsupported "regulatory delisting pressure" narrative that only became real after the replayed date; the model's own contradictory-evidence text admitted the claim wasn't grounded in supplied evidence, and it still materially influenced the outcome (drove an eventual SELL). Prompt mitigation shipped (ASSESSMENT_PROMPT_VERSION v1→v2, JUDGE_PROMPT_VERSION v2→v3). The 2022 FTX-window replay directly re-tested BTC/BNB under the new prompts: the same class of ungrounded historical-prior narrative recurred (assessment-level leakage is still present), but the Judge caught it every time and never let it drive a directional call (all 30 decisions landed WATCH/NO_TRADE).
    Precisely: assessment-level leakage remains present; Judge-level mitigation prevented the tested leakage from becoming a directional decision in the tested FTX scenario -- evidence the mitigation works in the cases tested, not proof it generalizes to every future leakage pattern. Do not mark this Done. Future validation criterion (not yet scheduled): test several more historically distinctive events from different regimes and verify unsupported historical priors are consistently detected and blocked every time, not just in the one tested window.

B. Engineering / Product / Operations backlog

Real, but not investment-validity blockers -- kept separate so they don't compete for priority with section A.

  • Open [HIGH][Risk] run_stress_test.py reads the system's own TARGET allocation, not real holdings — queries PortfolioPositionRepository.current_allocation instead of compute_current_allocations, the same real-vs-target ambiguity Phase 5c/5d fixed everywhere else. Real holdings can diverge from the system's target by 15-30+ percentage points for weeks (confirmed live for BTC/SOL), so this stress test's drawdown numbers may be computed against the wrong portfolio composition.
    An operational correctness issue affecting one diagnostic tool's output, not a research-validity question -- fix by reading real holdings the same way the Risk Engine and Judge context now do.

    Useful observability/product capability, but not a current investment-validity blocker. Needs a real backend design decision first (which sources, what endpoint shape) before any UI work.
