TODO

Real recommendations that came up while building/discussing this dashboard — not built (or not yet decided), kept here so they aren't lost. Static list, not derived from any live data.

  • Deferred A way to correct or remove a mistaken holdings entry — currently no delete exists at all (by design: the ledger is append-only). Two real options discussed: (a) a genuine hard delete, which breaks the append-only guarantee and several real downstream consequences (retroactive history corruption, current numbers shifting with no new action, past Judge decisions becoming unreproducible — see the full breakdown from that discussion); (b) a "Remove" button that posts an offsetting correcting transaction instead, preserving the audit trail.
    Verdict: "let's address this at a later point in time."
  • Open Revisit SCREENING_UNIVERSE_SIZE (currently 30) — this default was originally set because of a CoinGecko per-asset historical-endpoint rate limit, but that specific endpoint isn't even used by today's screening pipeline anymore (Binance/Coinbase supply volatility/drawdown instead, and the CoinGecko/CoinMarketCap universe calls are single batched requests regardless of size). Raising it would mainly mean more sequential Binance/Coinbase OHLCV calls (longer run time, not more real cost, and well within Binance's generous rate limits).
    Verdict: never formally decided either way — just an observation from investigating why 30 was chosen.
  • Open Reconcile assets.in_asset with real holdings data at the source — this column is set once at asset-creation time and never updated again, so it doesn't reflect current real holdings (confirmed live via "S"/Sonic: in_asset=true but zero real transactions ever recorded). The dashboard's own HELD badges were fixed to compute live from /holdings instead of trusting this column — but the column itself, in the database, is still permanently stale, which could bite anything else that ever reads it directly in the future.
  • Proposed evidence_observations has no API endpoint at all -- the single largest block of invisible data in the system — the entire evidence layer: funding rates, open interest, options IV, on-chain flows, DeFi TVL, stablecoin supply, macro CPI/PCE/Fed series, regulatory calendar -- dozens of heterogeneous JSONB payloads. Signal Sources' static text names the vendors but shows none of their actual collected data.
    Proposed fix: needs a real backend design decision first (which sources, what shape of endpoint) before any UI work -- not a quick add like the items above.
  • Declined asset_status_history (a pure audit trail) — recommend NOT surfacing — current state is already shown live via the SCREENED/JUDGED/HELD badges; this table is only the change-log behind them.
    Verdict: not worth a dedicated UI -- would be pure audit-log clutter with no decision-relevant content beyond what's already visible.
  • Declined portfolio_allocation_changes (a pure audit log) — recommend NOT surfacing — current allocation + the "Allocation last changed" timestamp already cover what this table would add.
    Verdict: redundant with what's already shown.
  • Declined prompt_templates.template_hash — recommend NOT surfacing — pure dedup/versioning bookkeeping (detects when a prompt's text changed), not decision-relevant to a dashboard viewer.
    Verdict: internal-only; showing it would add noise with no real interpretability.
  • Declined Raw LLM payloads (model_market_assessments.raw_response, llm_analyses.response/token_usage) — recommend NOT surfacing — debug-only raw payloads; real cost is already reported in dollar terms via Cost/spend.
    Verdict: would clutter the page with raw JSON for no real benefit over the dollar figures already shown.
